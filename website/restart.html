The one restart

Scrub through the install. Pull the plug anywhere.

Every step AurOS takes, in order, with what the screen says and what is on the disk at that moment. The installer names its own dangerous instants, and a test build can be told to stop dead at any one of them. Press Pull the plug and see what the tests found when the power went at that exact point.

    The named instants

    From src/aurstage/fault.h: a fault build stops dead at exactly one named instant, so every run is the same run and a failure can be reproduced by its name.

    Eighteen places the power was cut on purpose.

    Thirteen during the install and five during the restore, in tools/powercuttest.sh. 138 checks, all of them passed (docs/results/powercut.txt). Press one to jump there with the plug already pulled.

    What this does not prove

    The limits, in the test’s own words.

    • A disk’s own write cache. The tests run in a virtual machine, and its disk is not a real drive. What is tested is the order in which writes reach the disk and that each commit is one sector. Whether a particular drive lies about having saved what it was given is a property of that drive.
    • One firmware. The virtual machine’s UEFI firmware (OVMF), with Microsoft’s keys and Secure Boot on. It is not a laptop from 2014.
    • The middle of the shrink. No instant is named inside it, because nothing can make it safe. That is why the screen says “Do not turn the computer off” there and only there.
    • The memory stick. The power-cut runs used a machine with an AurOS memory stick, which holds the way back in that design. The test installer you can download today installs without one and keeps the way back on the disk; its install and its putting-back are tested end to end, but this set of power cuts has not been run in that mode.
    • A real PC. None of this has happened on a real PC’s disk yet.
