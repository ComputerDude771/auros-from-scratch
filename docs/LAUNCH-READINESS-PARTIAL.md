# Launch readiness — PARTIAL results (2026-10-23)
The `launch-readiness` workflow (`tools/workflows/launch-readiness.js`) was cut off by the usage limit. Four of seven dimensions were audited (data-safety, every-machine, journey, daily-use); commercial-legal, security and evidence were not; **no gap went through the skeptic check**. Re-run the workflow to produce `docs/LAUNCH-READINESS.md`. Verdict of every finished dimension: **not ready to charge money.**

## Dimension report (15 gaps)

1. On real hardware, AurOS has installed on 0 PCs. On a real-Windows VM, it has also installed 0 times: the only end-to-end run that reached the installer step stopped at "the download never finished" (e2e-39894079407 live.txt). No AurOS-Setup.exe release exists (the only releases are the e2e-*/othersys-* prereleases). Every staging install test runs on QEMU/OVMF with a virtio-blk disk. Windows 10, the target market, has never run the wizard anywhere (windows.yml runs on Windows Server; e2e runs on Win11 Enterprise 26100 only).
2. Refusals are well built and read-only, and each comes with a plain reason. Covered: ARM, BIOS/MBR, a db that only has the 2023 key, Secured-core, Intel RST NVMe/VMD remapping, too little space, a too-small ESP, dynamic disks, Storage Spaces, failing SMART, and running on battery. Most of these are proven only in simulation (matrixtest 10/10, nosticktest 2023-keys-only, Wine navtest). Two are partly proven on a real Windows Server VM in windows.yml: the RST device-tree walk and the ESP room check.
3. The worst every-machine risks come after the restart, where no test reaches. If the firmware ignores or prunes BootNext, or refuses shim, the PC comes back to Windows and nobody tells her. If the GPU, KMS or input fails while the hold is armed, the machine keeps booting AurOS's "sorry" screen on every start and never goes back to Windows. Broadcom wl/b43 Wi-Fi laptops end up offline with no store. Intel RAID volumes and Optane-cached disks pass preflight.
4. Coverage matrix:

- Intel/Realtek/Atheros/MediaTek Wi-Fi: likely works (inferred).
- Broadcom wl or b43: installs with no Wi-Fi.
- NVIDIA (nouveau)/AMD/Intel GPU: unknown, never on a real GPU.

- Windows 10: never tested. Windows 11: VM up to the download step.
5. Estimate for the target market (Win10 PCs that can't run Win11), inferred with no real-PC data: about 45-60% get through preflight. Most refusals are BIOS/MBR (about 20-35%, no authoritative data), plus space, 32-bit and RST. About 80-90% of those that pass end with a working, online desktop. So roughly 40-50% of attempts succeed and 40-50% are refused with a plain reason. About 5-12% fail silently or hit a broken or stuck result. Charging before a free compatibility check, with zero real-PC data, is not defensible.

## Dimension report (15 gaps)

1. The design is careful and well documented: offline shrink, a one-sector GPT commit, BootNext fallback, a saved copy of the start-up, BootOrder written only after 'yes'. It passes 138 power-cut checks and the install/put-back round trips, but all of it in QEMU against a 1 GiB mkntfs volume with 7 files.
2. Nothing destructive has ever run on a disk Windows created, or on any real PC. The real-Windows e2e has never got past the download, and plat_win.c's raw-disk and BitLocker code has never met a real machine.
3. The shipped mode has no memory stick, so the one documented data-loss window (a power cut during ntfsresize) has no recovery path, no backup step and no mid-resize test. The power-cut and geometry suites are a month old, ran in stick mode, and are not in CI.
4. Concrete code risks: BitLocker detection that is probably blind on an unlocked volume and only backstopped in staging; Put Windows back overwriting her live EFI partition with a stale snapshot; no way to remove AurOS from Windows; Windows partitions mountable read-write with no password; an undetected second install; and an install left armed after 'Not yet'.
5. Verdict for data safety: not ready to charge money.
