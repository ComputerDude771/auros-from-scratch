## Domain report (7 findings)

Staging's mechanics are unusually disciplined: a single build-time-enforced disk writer (wr.c) with armed, bounds-checked windows; all shell-outs use execv with fixed argv and numeric args (no shell, no untrusted strings to exec); the Windows volume is mounted read-only, nosuid/nodev/noexec with an ST_RDONLY recheck; the on-disk NTFS/GPT/journal/rescue parsers are written defensively with consistent overflow and extent checks; and the destructive path gates on health, power, surface tests, read-back verification, and a verified rescue copy before the one irreversible shrink. The weaknesses are at the trust boundaries, not in the arithmetic. The dominant one is structural and is in the product's own threat model: under Secure Boot the initrd is unsigned and unverified, so whatever is in staging.img runs as root pre-OS with the firmware still reporting 'secure', and the installed restore entry selects it by a filename search that any USB or second ESP satisfies — a bootkit and destructive-restore vector that the standing on-ESP payload keeps alive for the life of the machine. The second class is self-certifying inputs: the no-stick image is validated only against its own co-located manifest, and the restore accepts an unkeyed, size-matched rescue blob when the live GPT is unreadable, so a Windows-side or evil-maid attacker can substitute the whole OS or rewrite the disk layout. Highest-value fixes that respect the no-signing constraint: carry the image hash and a pinned restore-partition identity in the installer-written journal, drop filename-based boot searches, stop leaving the unsigned payload on the ESP, and avoid mounting attacker NTFS with ntfs3.
- **[critical] Unverified initramfs runs as root under a valid Secure Boot chain; the restore entry selects it by filename search across every disk and USB stick** (perf: none; files: rootfs/usr/lib/auros/grub.cfg.in; src/aurbridge/phases.c; src/aurstage/install.c (post-install ESP cleanup); rootfs/usr/lib/auros/answer.sh; rootfs/usr/lib/auros/bootchain)
  - Attack: The destructive engine boots MS-signed shim -> Canonical grub -> Canonical-signed kernel (staging.efi) -> UNSIGNED initrd (staging.img). shim/grub/the kernel verify each other; nothing verifies the initrd, so whatever is in staging.img executes as PID 1 with full block-device write access while the firmware still reports Secure Boot = on. The installed restore menu entry locates the payload with `search --no-floppy --file --set=root /EFI/AurOS/staging.efi`, which matches the FIRST partition on ANY attached disk or USB that has that path. An attacker (BadUSB / evil maid / any process that can write a FAT volume) drops a real Canonical kernel as staging.efi plus a malicious staging.img and a crafted boot entry; on the next boot or when the non-technical user picks 'Put Windows back', their initrd runs as root pre-OS. This is a persistent, Secure-Boot-preserving bootkit staging ground and a way to trigger the destructive restore against a chosen disk. The journal/record safety gates do not help because the attacker ships their own init that ignores them.
  - Evidence: build/staging:570 packs the initrd as `cpio --format=newc | gzip` with no signature or hash; src/aurbridge/phases.c:1591-1613 copies staging.img to the ESP and phases.c:1738 sets BootNext to it; rootfs/usr/lib/auros/grub.cfg.in:113 and :121-122 use `search --no-floppy --file` then `linux .../staging.efi aurstage.restore` + `initrd .../staging.img`; rootfs/usr/lib/auros/bootchain (judge_shim/judge_loads) and answer.sh verify shim, grub and kernel against db/dbx/SBAT but never the initrd.
  - Control: In grub.cfg.in pin the restore entry's root to the partition the installer recorded (a fixed `(hdX,gptY)`/`--hint`/PARTUUID) and delete the `search --no-floppy --file` fallback so a second ESP or USB cannot be chosen; after a successful install remove staging.efi/staging.img/grub.cfg from the ESP (see finding on the standing payload) and recreate them transiently only while a restore is actually requested. Document the residual (an attacker who overwrites the real in-place initrd still wins) since it cannot be closed without signing/MOK, which the product forbids.
  - Test: Boot the real image under OVMF with Microsoft keys and Secure Boot ON, with a SECOND FAT volume present that contains /EFI/AurOS/staging.efi (real kernel) and a marker staging.img; invoke the restore entry. The test passes only if grub refuses to boot the second volume's initrd (root is pinned to the recorded partition). Static gate: `grep -n 'search --no-floppy --file' rootfs/usr/lib/auros/grub.cfg.in` must return nothing inside the put-windows-back block.
- **[high] No-stick AurOS image is self-certifying: staging checks the image hash against the attacker-writable manifest, and nothing pins it to a value the trusted installer baked in** (perf: low; files: src/aurbridge/format.c and src/aurbridge/phases.c (add image_sha256 to the journal); src/aurstage/journal.c/journal.h; src/aurstage/install.c; src/aurstage/image.c)
  - Attack: In no-stick mode the image and its manifest live on the Windows NTFS partition (C:\AurOS\auros-<profile>.img and .img.manifest). image_verify() compares the written root filesystem against root_sha read FROM THAT MANIFEST, not against any value carried in the journal or baked into the installer. A SHA-256 is not a secret, so any code that can write C:\AurOS\ (ordinary malware already on Windows, or an attacker who wins the download->reboot TOCTOU) replaces the .img with a backdoored AurOS rootfs and recomputes a matching manifest; staging verifies it against the attacker's own hash, writes it to the new root partition, and boots it. The victim then runs an attacker-controlled OS as their daily driver. The journal gates only disk/partition identity, never image content.
  - Evidence: src/aurstage/image.c image_verify() hashes and compares to s->root_sha, which image_find_file() reads from man+36 of the on-NTFS manifest (image.c ~lines 356-397, 461-491); src/aurstage/install.c:430-434 builds the image/manifest paths on the mounted Windows volume; the journal struct (src/aurbridge/format.c fmt_journal_json and src/aurstage/journal.h) carries disk serial/LBA/GPT sha but no image hash.
  - Control: Have the elevated Windows installer write the expected image root SHA-256 (it already knows AUROS_IMAGE_SHA256) into the journal, and have install_run compare the manifest/image hash to the journal value before image_write_root. This binds the image to the one artifact the trusted installer vouched for and closes the Windows-partition-only attacker.
  - Test: In nosticktest/installtest, after the installer writes the journal, tamper the .img on the Windows volume and regenerate its manifest to match the new bytes. Install must refuse with a hash-mismatch verdict. Remove the control and the same tampered image installs and boots, proving the test exercises it.
- **[high] Restore writes an attacker's partition table and ESP to the internal disk when the live GPT is unreadable, because the disk-identity check is skipped in that case** (perf: none; files: src/aurstage/rescue.c (rescue_restore identity gate); src/aurstage/install.c (restore source gating))
  - Attack: rescue_restore() only enforces that the saved copy's disk GUID equals the live disk's GUID when the live GPT could be read (`if (live_ok && memcmp(...))`). When the live GPT is absent/corrupt it falls back to size-only matching (live_bytes == p.disk_bytes). The rescue payload is integrity-checked with CRC32 + SHA-256, neither of which is keyed, so an attacker can author a wholly valid rescue blob sized to the target. Evil maid: wipe/corrupt the target's GPT, plug a USB whose rescue area carries a size-matched payload for a different disk GUID, and have the user (or themselves) run 'Put Windows back'. The internal disk's GPT, backup GPT and ESP region are overwritten from the stick. The fde_guard/head_is_a_filesystem guards stop clobbering a BitLocker or live NTFS head, but the ESP contents and table come straight from the attacker's blob, seeding an attacker bootloader layout.
  - Evidence: src/aurstage/rescue.c: hdr_unpack validates only CRC32 (rescue.c ~line 256) and rescue_verify checks only SHA-256 (~line 684); rescue_find_n scans all disks including removable (~line 65); in rescue_restore the GUID check is `if (live_ok && memcmp(live.disk_guid, cap_hdr+56,16)...)` (~line 1185), so !live_ok bypasses identity and only `live_bytes != p.disk_bytes` (~line 1120) remains.
  - Control: Refuse to restore from a removable source onto a disk whose live GPT is unreadable (require the on-target saved copy, which rescue already prefers, to be the authority), or require an explicit user-confirmed disk match before writing when identity cannot be proven. Keep the size check as a necessary-not-sufficient test.
  - Test: putbacktest variant: corrupt the target disk's primary+backup GPT, attach a stick holding a CRC/SHA-valid rescue payload whose stored disk GUID differs but whose disk_bytes matches. rescue_restore must return refusal and write nothing (wr_untouched). Without the fix it restores the attacker table/ESP.
- **[medium] Journal profile/image_on strings are used to build filesystem paths and drive control flow with no character validation** (perf: none; files: src/aurstage/journal.c)
  - Attack: install_run builds the image path as snprintf(ip,"%s/AurOS/auros-%s.img", winroot, j.profile) using j.profile straight from the journal, which in no-stick mode is the sole machine-identity gate and resides in the attacker-mutable staging.img. profile is never constrained to the five known names, so `../` or other components are accepted; image_on likewise selects code paths. Impact is bounded today (the target is the read-only, attacker-owned Windows mount), but the only reason it is not worse is incidental, and this is the layer the whole safety model trusts.
  - Evidence: src/aurstage/journal.c read_string/STR macro store profile/image_on with no charset filter (journal.c ~line 107-119); src/aurstage/install.c:431 uses j.profile in the path; main.c/install.c branch on image_on.
  - Control: In journal_read, reject the record unless profile matches a strict allowlist ([a-z-]+, one of the five profiles) and image_on is exactly 'stick' or 'windows'. Fail closed as journal_read already does for missing fields.
  - Test: Feed a journal with profile='../../x' or image_on='../' to journal_read; it must return 0 (rejected) and install_run must refuse. A unit test over journal.c asserts allowlist rejection; today it is accepted.
- **[medium] No-stick mode mounts the attacker-controllable Windows volume with the in-kernel ntfs3 driver, exposing a kernel memory-safety surface in the root staging environment** (perf: medium; files: src/aurstage/winvol.c; src/aurstage/install.c; src/aurstage/image.c; src/aurstage/ntfs.c)
  - Attack: To read the image file in no-stick mode, winvol_mount() modprobes ntfs3 and mounts the Windows NTFS. ntfs3 is a comparatively young driver with a recurring history of out-of-bounds and use-after-free bugs on malformed metadata. An attacker who controls the Windows volume (the realistic precondition for several of these attacks) can craft NTFS structures that trigger ntfs3 bugs, yielding code execution in the kernel of the staging environment, which is already the most privileged, pre-OS context on the machine. Staging's own ntfs.c reads the raw device safely for state, but the mount bypasses that hardened path entirely.
  - Evidence: src/aurstage/winvol.c load_ntfs3() + mount(windev,...,"ntfs3",MS_RDONLY|MS_NOSUID|MS_NODEV|MS_NOEXEC,...); build/staging:534 ships kernel/fs/ntfs3; the hardened reader in src/aurstage/ntfs.c operates on the raw device and is not used to fetch the image.
  - Control: Avoid mounting: locate and read the image by its recorded byte extent on the NTFS partition using the existing raw-device reader (extend ntfs.c to resolve the one well-known file, or record its LBA run in the journal at install time), or require the memory stick for machines whose Windows volume is not trusted. If mounting must stay, fuzz ntfs3 inputs and pin to a patched kernel.
  - Test: Run staging's no-stick image-read path under a malformed-NTFS corpus in KVM (ntfs3 with panic_on_warn=1); no oops/panic. A scratch harness mutates a minimal NTFS and mounts it read-only to confirm the mount is no longer on the image-read path once the control lands.
- **[medium] The unsigned staging payload and its boot entry are left on the ESP permanently after install, so the pre-OS root vector is a standing offline target on every machine** (perf: low; files: src/aurstage/install.c; rootfs/usr/lib/auros/grub.cfg.in; rootfs/usr/lib/auros/answer.sh; src/aurfirst/state.c)
  - Attack: After a successful install the installer's staging.efi, staging.img and grub.cfg remain on the machine's ESP because the restore feature depends on finding them there. That turns the unsigned-initrd-runs-as-root chain (finding 1) from a one-restart exposure into a permanent one: any later offline/admin write to the ESP, or a swapped disk, can replace staging.img and own the next boot of the restore entry, with Secure Boot still green. It also keeps a destructive, unauthenticated 'reformat this disk' tool one grub menu pick away for the life of the machine.
  - Evidence: rootfs/usr/lib/auros/grub.cfg.in restore block and rootfs/usr/lib/auros/answer.sh staging_present() both require /EFI/AurOS/staging.efi+staging.img to exist on an EFI partition; src/aurstage/install.c never removes them post-install; src/aurbridge/preflight.c:1390 and phases.c:1456 only clean PRIOR attempts before a new write.
  - Control: Stop storing the restore payload on the ESP long-term: keep the staging kernel/initrd in the AurOS recovery partition and have the restore flow stage them to the ESP only for the duration of one restore, removing them again. The ESP then carries no standing unsigned-root payload.
  - Test: After installtest completes, assert no /EFI/AurOS/staging.efi or staging.img remains on the ESP, and that a restore request stages then removes them (check before/after). Today the files persist, which the assertion catches.
- **[low] GPT entry array is read from an attacker-chosen LBA with only a CRC gate, no bound that the array lies within the disk or clear of partition data** (perf: none; files: src/aurstage/gpt.c)
  - Attack: gpt_read/parse_entries read n_entries*entry_size bytes from entry_lba*sector, validating n_entries<=GPT_MAX_ENT and entry_size<=4096 and the CRC32 over the array, but not that entry_lba is within the disk or does not point into partition payload. An attacker crafting a GPT on a plugged-in disk (or the image) can aim the array read anywhere on that device. Impact is limited (read-only, CRC-gated, bounded size) so this is defense-in-depth, but on a 4Kn vs 512 mismatch or a huge entry_lba it is an unvalidated seek driven by on-disk data.
  - Evidence: src/aurstage/gpt.c parse_header sets entry_lba=rd64(h+72) with no range check; parse_entries reads at entry_lba*sector (gpt.c ~lines 100, 118) guarded only by the CRC at h+88.
  - Control: In parse_header reject entry_lba < 2 or entry_lba*sector + n_entries*entry_size > disk_bytes (and for the primary, that it sits below first_usable). Cheap arithmetic before the read.
  - Test: Hand gpt_read a header whose entry_lba points past the device or into the first partition; it must return -1 before issuing the read. A unit test with a synthetic header asserts rejection.

## Domain report (7 findings)

AurBridge is carefully written for reliability and its parsers are robust: 5,000,000 ASan+UBSan fuzz iterations against the gzip inflater (src/aurbridge/inflate.c, compiled and fuzzed in scratch) found zero memory-safety or UB defects, the piece-list parser rejects path traversal and non-printable bytes, the journal JSON is properly escaped, and the whole-image SHA-256 + gzip CRC make the download path integrity-safe end to end. The serious weaknesses are all in the Windows trust boundary around an UNSIGNED, elevated exe that a non-technical user runs from Downloads. Two are critical: (1) no safe DLL search (no SetDefaultDllDirectories, non-KnownDLL static imports winhttp/setupapi/cfgmgr32 plus a bare LoadLibrary of dwmapi) means a planted DLL in Downloads gets elevated code execution; (2) in the default no-stick flow the root-running staging environment trusts an attacker-writable manifest in the predictable, world-creatable C:\AurOS, and the trusted ESP journal carries no image hash, so a swapped image+manifest installs an attacker OS as root. High-severity issues: an unguarded AURBRIDGE_STAGING_KARGS env var injects kernel/grub.cfg content at the install boot via the inherited elevated environment, and the elevated resume scheduled task (/rl highest) re-runs the un-reverified installer from its user-writable Downloads path. Remaining items (http:// download acceptance, squattable single-instance mutex, unhashed %TEMP% payloads) are medium/low. Fixes are cheap on a 2013 4 GB laptop — all are one-time startup/compile-time changes with none-to-low runtime cost. Priority order: lock the DLL search, bind staging to a journal-carried image hash and harden the C:\AurOS ACL, compile-gate the kargs backdoor, then move the resume binary to an admin-only path.
- **[critical] Elevated installer is DLL-search-order hijackable from the Downloads folder (winhttp/setupapi/cfgmgr32 static imports + runtime dwmapi)** (perf: none; files: src/aurbridge/wizard.c, src/aurbridge/main.c, build/aurbridge)
  - Attack: The wizard runs requireAdministrator (src/aurbridge/aurbridge.manifest). Nothing in the codebase calls SetDefaultDllDirectories, SetDllDirectory, SetSearchPathMode, or delay-loads anything (grep for all of these returns empty). The PE statically imports WINHTTP.dll, SETUPAPI.dll and cfgmgr32.dll (build/aurbridge links -lwinhttp -lsetupapi -lcfgmgr32; objdump -p confirms the import table) and additionally does bare LoadLibraryW(L"dwmapi.dll") at wizard.c:3081. None of those four DLLs are KnownDLLs, so Windows resolves them from the application directory first. A great-grandmother double-clicks AurBridge.exe sitting in C:\Users\her\Downloads; any malicious winhttp.dll / setupapi.dll / cfgmgr32.dll that a drive-by download, malicious ZIP, or earlier malware dropped into that same folder is loaded and its DllMain runs at Administrator integrity before WinMain or the single-instance mutex, giving full elevated code execution. This is the exact 'DLL hijacking of downloaded installers' case in the threat model.
  - Evidence: src/aurbridge/aurbridge.manifest:9 requireAdministrator; build/aurbridge link line `-lwinhttp -lsetupapi -lcfgmgr32`; objdump -p out/aurbridge-wizard.exe shows DLL Name: WINHTTP.dll / SETUPAPI.dll and DllCharacteristics 0x160 (ASLR/NX only, no safe-search); src/aurbridge/wizard.c:3081 `HMODULE m = LoadLibraryW(L"dwmapi.dll")`; repo-wide grep for SetDefaultDllDirectories/SetDllDirectory/LOAD_LIBRARY_SEARCH/delayload = 0 hits.
  - Control: As the first statements in both main() (main.c) and WinMain() (wizard.c), call SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32) (available since the Win7 KB2533623 update AurBridge already targets). Convert the three non-KnownDLL static imports to delay-loads in build/aurbridge (`-Wl,--delayload=winhttp.dll,--delayload=setupapi.dll,--delayload=cfgmgr32.dll -ldelayimp`) so they resolve only after the search path is locked. Replace wizard.c:3081 with LoadLibraryExW(L"dwmapi.dll", NULL, LOAD_LIBRARY_SEARCH_SYSTEM32). Set linker DllCharacteristics flag FORCE_INTEGRITY not needed, but add /DEPENDENTLOADFLAG equivalent is unavailable in mingw so delay-load is the real fix.
  - Test: Build the wizard, drop a stub winhttp.dll (and setupapi.dll) whose DllMain writes a marker file next to aurbridge-wizard.exe, run it from that directory, and assert the marker is NOT created and WinHttp calls still resolve to System32. Without the SetDefaultDllDirectories+delayload change the marker file appears (hijack succeeded); with it, it never does. A CI check can also assert objdump -p lists winhttp/setupapi/cfgmgr32 only under the Delay Import Directory, not the normal Import Table.
- **[critical] No-stick staging trusts an attacker-writable manifest in C:\AurOS; the trusted journal carries no image hash, so a swapped image+manifest installs an attacker's root filesystem** (perf: low; files: src/aurbridge/format.h, src/aurbridge/format.c, src/aurbridge/phases.c, src/aurbridge/plat_win.c, src/aurstage/install.c, src/aurstage/journal.h)
  - Attack: In the default (no memory stick) grandma path the image and its describing manifest are written to C:\AurOS\auros-desktop.img[.manifest] (wizard.c:1255, phases.c:1382-1387). C:\AurOS is created with CreateDirectoryW(w, NULL) and the ERROR_ALREADY_EXISTS is ignored (plat_win.c:747-756, make_dirs), so it inherits the default C:\ root ACL. Standard users have Create-Folders on C:\ root by default, so a non-admin (or malware running as her) can PRE-CREATE and own C:\AurOS, or simply add files to it. After the elevated prepare phase finishes and before the one-shot staging reboot actually runs, the attacker replaces both auros-desktop.img and auros-desktop.img.manifest with a malicious rootfs and a self-consistent manifest. After reboot the staging environment runs as root and, in no-stick mode, reads the image hashes FROM THAT co-located manifest (src/aurstage/install.c image_find_file -> image_verify) — the ESP-resident journal, which is the only trusted channel the elevated installer wrote, contains disk_serial/model/gpt_sha256/profile but NO image or root/esp hash (fmt_journal in format.h:52-106). Staging therefore cannot tell the image was swapped and installs the attacker's operating system as her new OS. Full install-time root compromise of 'the secure OS'.
  - Evidence: src/aurbridge/wizard.c:1255 image_path = "%s\\AurOS\\auros-desktop.img" on SystemDrive; src/aurbridge/plat_win.c:754 `CreateDirectoryW(w, NULL)` (no SECURITY_ATTRIBUTES, result unchecked); src/aurbridge/phases.c:1378-1393 writes/reads back the .manifest beside the image; src/aurstage/install.c:~430 image_find_file(ip, mp, j.profile,...) then image_verify against manifest-supplied root_sha/esp_sha; src/aurbridge/format.h:52-106 fmt_journal has no image hash field.
  - Control: (1) Carry the baked image SHA-256 (c->image_sha256, already trusted — it is compiled into the signed-by-behaviour exe) into the journal struct (format.h fmt_journal + fmt_journal_json in format.c) and have staging reject any image/manifest whose root+esp hashes are not consistent with that journal-carried value (src/aurstage/install.c, journal.h). (2) Stop using a predictable world-writable path: create the staging dir with an explicit DACL granting only SYSTEM+Administrators (build a SECURITY_ATTRIBUTES from an SDDL like "D:PAI(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)" and pass it to a new secured make_dirs), and if the directory already exists verify its owner is Administrators/SYSTEM and reset the ACL (or refuse) before writing. Either fix alone closes it; do both.
  - Test: In the aurbridge-sim / aurstage harness, prepare a no-stick install, then (as the 'attacker') overwrite auros-<profile>.img and regenerate a self-consistent .manifest for a different rootfs, and run the staging installer. It must refuse with an image-mismatch verdict because the journal-carried hash no longer matches. Without the journal-hash binding the swapped image installs silently. Second test: pre-create the staging directory as a non-admin user and assert the installer either resets its ACL (icacls shows only SYSTEM/Administrators) or refuses.
- **[high] Unconditional AURBRIDGE_STAGING_KARGS environment variable injects attacker-controlled kernel command line / grub.cfg script at the elevated install boot** (perf: none; files: src/aurbridge/phases.c, build/aurbridge)
  - Attack: phases.c:1641 reads `getenv("AURBRIDGE_STAGING_KARGS")` with only a `/* tests only */` comment and no compile-time guard, then splices the raw string into the ESP grub.cfg menuentry (phases.c:1678-1682) and into the UEFI boot entry command line (phases.c:1724-1727) via snprintf "%s". When a standard user double-clicks the installer, UAC elevates a child that INHERITS the user's environment, so the user can set AURBRIDGE_STAGING_KARGS beforehand and have the elevated installer write arbitrary kernel arguments (e.g. init=/bin/sh, rd.break, aurstage.* overrides) onto the ESP. Because the value is placed into the line-oriented grub.cfg without stripping newlines, a value containing a newline injects entire new grub script directives (a second `linux ... init=/bin/sh` line or a different menuentry). Signed shim->grub->kernel then boot those arguments as root during install, subverting the very install that is supposed to produce a secure system.
  - Evidence: src/aurbridge/phases.c:1641 `const char *extra = getenv("AURBRIDGE_STAGING_KARGS");  /* tests only */` with no #ifdef; used at phases.c:1679 (grub.cfg `...console=tty0%s%s`) and phases.c:1726 (boot entry cmdline); no sanitization of newlines or shell/grub metacharacters; grep shows it is the only getenv in the Windows build.
  - Control: Gate the env-var path behind a build-time flag that release builds never set (e.g. `#ifdef AUROS_DEV` around the getenv, else extra=NULL), mirroring how build/aurbridge already uses AUROS_RELEASE. Independently, reject any value that contains a byte outside a strict allowlist (printable, no newline/CR, no quote) before it reaches grub.cfg, and length-bound it. The grub.cfg writer should also refuse to emit a cfg whose menuentry body spans more than the expected single linux/initrd pair.
  - Test: Run the sim/handoff phase with AURBRIDGE_STAGING_KARGS set to `foo\nmenuentry evil { linux /x init=/bin/sh }` in a release-configured build and assert the generated grub.cfg contains no extra menuentry and no injected init= (and that the env var is ignored entirely). A dev build with AUROS_DEV may still honour a sanitized single-line value. Without the guard the evil menuentry/newline lands in grub.cfg.
- **[high] Elevated resume scheduled task re-launches the installer binary from its user-writable Downloads path with highest privileges and never re-verifies it** (perf: low; files: src/aurbridge/fix_win.c, src/aurbridge/plat_win.c, src/aurbridge/wizard.c)
  - Attack: fix_resume_arm (fix_win.c:331-352) creates a scheduled task `schtasks /create /sc onlogon /it /rl highest /ru <domain>\<user> /tr "\"<self>\" --resume"` where <self> is GetModuleFileNameW of the running exe — i.e. the original download location such as C:\Users\her\Downloads\AurBridge.exe. That path is writable by the standard user (and by any malware running as her). The task runs at the next logon with highest (elevated) rights. Between arming the task and that logon, anything running as the user can overwrite the Downloads exe with its own payload and Task Scheduler will execute it elevated — a clean user-to-admin escalation / persistence primitive. On --resume the wizard performs no hash/signature check of itself (wizard.c:4024/4093 just set resume=1 and proceed), so the substitution is undetectable. This is precisely the 'elevated scheduled task pointing at a user-writable file' item in the threat model, and it is present.
  - Evidence: src/aurbridge/fix_win.c:338-349 builds the schtasks command with `/rl highest` and `/tr \"%s\" --resume` where %s is the module path; src/aurbridge/wizard.c:4023-4032 and 4093-4096 handle --resume with no integrity check; the module path is the Downloads location because that is where the user ran it.
  - Control: Before arming, copy the running exe into an Administrators/SYSTEM-only directory (e.g. the hardened C:\AurOS from finding #2 or %ProgramData%\AurOS with an explicit DACL) and point the task's /tr at that protected copy, not at the Downloads path. Store the SHA-256 of the copied binary (e.g. in the ESP journal or a protected file) and verify it at --resume startup, refusing to continue if it does not match. Prefer /rl highest only on the protected copy.
  - Test: Arm the resume task, then (as a standard user) overwrite the file the task's /tr points at with a different binary and trigger the task. With the fix the /tr target lives in an admin-only directory the user cannot overwrite and the --resume self-hash check fails on tampering (installer refuses); without it, the attacker binary runs elevated.   - Attack: A hostile hotspot, a rogue IPv6 RA/RDNSS, or DNS-changer malware on an old ISP router (common and long-lived) controls every name lookup. HTTPS-only mode stops silent page substitution, but the attacker still sees every site she visits. They can steer non-browser clients and can redirect lookalike or typo traffic to scam pages that carry valid certs. A filtering resolver would block known scam and malware domains at no cost, and nothing uses one.
  - Evidence: rootfs/etc/NetworkManager/conf.d/10-dns-resolved.conf: `dns=default`, `rc-manager=file` (NM writes DHCP/RA DNS servers directly). No systemd-resolved, so no DNSSEC/DoT. rootfs/etc/firefox/policies/policies.json has no DNSOverHTTPS key.
  - Control: In policies.json add `"DNSOverHTTPS": {"Enabled": true, "ProviderURL": "https://dns.quad9.net/dns-query", "Fallback": true, "Locked": true}`. Quad9 is a malware/phishing-blocking resolver, and fallback keeps captive portals working. If systemd-resolved is ever added, ship resolved.conf with `LLMNR=no`, `MulticastDNS=no`, `DNSOverTLS=opportunistic`, so no new 5355 listener appears.
  - Test: `jq -e '.policies.DNSOverHTTPS.Enabled == true' /etc/firefox/policies/policies.json`. KVM: the peer router runs dnsmasq with `address=/example.org/10.0.2.99`. Without the control the load fails or goes to 10.0.2.99.
